# Git、分支、Issue 与 PR：协作入门

这是一份给项目协作者的实用说明。目标不是记住所有 Git 命令，而是知道每个对象负责什么、什么时候该合并，以及怎样避免把已验证的工作重复合并。

## 先记住四件事

| 名称 | 它是什么 | 用来解决什么 |
| --- | --- | --- |
| 本地仓库 / worktree | 电脑上的一份工作目录 | 在不影响主线的情况下编写、测试和检查改动 |
| 分支 | 一条独立的提交历史 | 把一项工作与 `main` 隔离开 |
| Issue | 一个待解决的问题或目标 | 说明为什么要做、验收什么、由谁跟进 |
| Pull Request（PR） | 把一个分支合入另一个分支的提议 | 让人审查改动、运行 CI，并留下可追溯的合并记录 |

`main` 是团队共同认可的主线。它不是每个人在本地随手拼接分支的地方；通常应由一个经过检查的 PR 合并进去。

## 正常的协作流程

1. 先用 Issue 记录问题、范围和验收条件。
2. 从 `main` 建一个分支；需要并行工作时，可以给该分支建一个独立 worktree。
3. 在自己的 worktree 修改、测试并提交。提交是本地历史记录，尚未影响其他人。
4. 把分支推到 GitHub，创建 PR。PR 的目标通常是 `main`，也可能是另一个尚未合并的前置分支。
5. CI 在 PR 上运行自动检查；协作者查看差异、测试结果和风险。
6. 当范围完成、检查通过、需要的人工验证完成后，把 PR 标为 ready for review，并由有合并权限的人合并。
7. 合并后重新读取 `main`、部署和关联 Issue 的状态；确认无误后，再清理已经不需要的分支和 worktree。

```text
Issue → 分支 / worktree → 改动与测试 → commit → PR（draft）
      → CI 与审查 → PR（ready）→ 合并到 main → 部署/回读 → 关闭 Issue 与清理
```

## Draft PR 不是失败状态

Draft 的意思是“这份改动还不请求正式合并”。常见原因包括：

- 改动还在拆分、串联或补测试；
- 需要先看 CI 是否能在真实合并组合中通过；
- 作者希望先让协作者看到实现方向，但还不希望它被误合并；
- PR 依赖另一个还没进入 `main` 的前置 PR。

Ready for review 则表示“这个 PR 已具备被正式审查和合并的条件”。CI 变绿是必要信号之一，但不自动等于可以发布：涉及界面、真机、签名、部署或数据的改动，仍要完成相应的人工或运行时验证。

## 谁应该合并 PR？

没有唯一答案，取决于仓库权限和团队约定：

- 在多人团队中，作者通常负责实现、更新 PR 和回应意见；审查者或维护者负责批准和合并。
- 在个人仓库或小团队中，作者也可以在检查通过后自行合并，但仍应先确认目标分支、CI、部署影响和未解决的审查意见。
- 分支保护规则、CODEOWNERS 和项目发布规则优先于个人习惯。

无论是谁点“Merge”，都不需要先把所有分支手工合并到本地 `main`。GitHub 上的 PR 合并才是共享主线的正式动作。合并后，本地再用 `git fetch` 和 `git pull --ff-only` 同步 `main` 即可。

## 本次审查整改应怎样合并

本次 2026-07-25 审查的组件 PR 是 #15 至 #25；其中一些是叠放（stacked）PR，目标分支并不直接是 `main`。它们的作用是让每个整改切片可以独立检查和回滚。

PR [#26](https://github.com/rwang23/awesome-codex-theme/pull/26) 已把这些组件整合到同一个分支，并以 `main` 为目标。它的正文包含 `Closes #4` 到 `Closes #14`，因此只要 #26 真正合并到 `main`，GitHub 就会自动关闭这 11 个审查整改 Issue。

正确的合并单位是 #26，而不是再逐个合并 #15 至 #25。逐个合并会重复引入已经被整合的提交，容易制造冲突、重复 CI 和难以解释的历史。

Issue #1 和 #2 不在 #26 的自动关闭清单中，应作为独立工作另行判断，不能因为审查整改 PR 合并就假定它们已经解决。

## 合并 #26 前后的检查表

合并前：

- 确认 #26 的目标仍是 `main`，源分支仍是预期的整合分支。
- 重新读取 PR 的提交、差异、合并状态和所有必需 CI 结果。
- 确认需要的浏览器、真机、签名或安全验证没有被“CI 绿色”替代。
- 确认这次合并会触发什么部署；如果会影响公开站点或用户，应取得针对该动作的明确授权。
- 确认不需要再分别合并 #15 至 #25。

合并时：

1. 将 #26 从 draft 转为 ready for review。
2. 完成最终审查后，在 GitHub 将 #26 合并到 `main`。选择 squash、merge commit 还是 rebase，要遵循仓库既有约定。
3. 不在另一个本地 worktree 里做第二次“手工总合并”。

合并后：

1. 读取远端 `main`，确认它已经包含预期的合并提交。
2. 读取部署/Pages 的实际状态，并做与改动相称的公开页面或运行时检查。
3. 确认 #4 至 #14 已被 GitHub 自动关闭；如有遗漏，检查 PR 描述中的关闭关键词和合并目标。
4. 在本地同步 `main`，例如先 `git fetch origin`，再在干净的主工作目录执行 `git pull --ff-only`。
5. 等上述回读完成后，再删除已合并的远端分支和对应 worktree；不要清理仍有未合并工作或用户文件的目录。

## 常见误解

**“所有 CI 都绿了，是不是一定该合并？”**

不一定。CI 证明自动化检查通过；它不自动证明真机行为、部署结果、发布签名、用户数据安全或产品取舍已经确认。

**“Draft PR 需要先在本地合进 main 才能转正式吗？”**

不需要。draft/ready 是 GitHub 上的审查状态。本地 worktree 只用于准备和验证改动；正式共享合并在 PR 上完成。

**“Issue 现在还是 Open，是不是说明实现没有完成？”**

不一定。很多团队会让 PR 使用 `Closes #编号`，并只在 PR 合入默认分支后自动关闭 Issue。这样 Issue 的状态才与用户真正拿到的主线版本一致。

**“分支和 worktree 是不是同一个东西？”**

不是。分支是提交历史；worktree 是该历史在磁盘上的一个工作目录。一个仓库可以有多个 worktree，它们分别检出不同分支，便于并行检查而不互相覆盖文件。

## 一句话规则

一项工作只有在“PR 已合入目标分支，并完成合并后的必要回读”后，才可以说它已经进入主线；在此之前，draft、分支和本地 worktree 都只是受控的准备状态。
