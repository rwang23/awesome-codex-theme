# 01 · 执行摘要

## 1. 产品成熟度判断

这个仓库已经具备成熟开源产品的多数组成部分：清晰的主题标准、11 个集合、68 套主题、136 个明暗模式、Registry、Schema、无代码归档、Gallery、桌面管理器、实机证据、双语文档和发布工作流。它的产品完成度明显高于一般“壁纸 + CSS”项目。

但工程成熟度存在不均衡：**信任边界与内容完整性设计较强，构建性能、事务恢复、UI 可访问性和 CI 供应链相对薄弱**。这意味着项目短期可以继续公开展示和接受内容贡献，但在扩大用户规模、频繁发布 Theme Manager 或把持久化 Full Skin 作为稳定能力前，应先完成 P1 修复。

## 3. 最关键的结论

### 3.1 生成器已经成为项目增长的主要瓶颈

当前生成器顺序处理 68 套主题，每套生成 4 张 PNG，并把大量产物保留在全局 `Map` 后统一写入。代表性主题仅一个 960×540 Light 与一个 2560×1440 Light 输出就用时约 21.19 秒；全量生成在审查环境超过 20 分钟仍未完成。随着主题继续增长，这会直接放大开发等待、CI 分钟、内存与失败重试成本。

### 3.2 仓库的默认命令契约不符合新贡献者直觉

在干净检出中直接运行 `npm test`，20 项中 6 项因为缺少生成的 `themes/registry.json` 失败；`npm run validate` 和 `npm run build` 也立即失败。README 虽给出了先生成再验证的顺序，但命令自身没有清晰区分“源码测试”和“生成物测试”，降低了本地调试与 CI 故障定位效率。

### 3.3 Full Skin 应用需要从“命令序列”升级为“事务”

当前代码先清理旧 Session，再准备新主题；多 target 注入任一失败会提前返回，却不会回滚已经成功的页面。监控连续失败后也可能静默退出，而 UI 仍认为主题 active。这个问题比单纯的样式 Bug 更重要，因为它决定用户是否能可靠恢复到旧主题或 Native 状态。

### 3.4 网络限制是在校验之前，而不是内存分配之前

Catalog、Registry 和 PNG 都有字节数、签名与 SHA-256 检查，这是明显优点；但部分路径仍先调用 `.bytes()` 把响应全部缓冲，再检查实际大小。Chunked 响应或虚假 Content-Length 可以在拒绝前占用过多内存。应改成按 chunk 累计并硬停止。

### 3.5 Gallery 与 Theme Manager 正在支付“证据图即列表图”的成本

136 张当前实机截图总计约 128.4 MiB。Gallery 卡片滚动后加载 1440×810 PNG；Desktop 又为列表创建大量图片节点并在筛选/模式切换时重建。实机 PNG 应继续作为证据保存，但列表需要专门的 320/480/960 WebP/AVIF 层。

### 3.6 可访问性问题主要来自“声明了复杂语义，却没有实现完整交互”

Theme Manager 使用 `tablist`、`listbox`、`option` 和自定义 `dialog` 语义，但没有完整 Arrow/Home/End、roving tabindex、focus trap、背景 inert 和焦点恢复。最佳修复不是继续添加 ARIA，而是先判断是否真的需要复合组件；能用普通按钮和原生 `<dialog>` 时优先使用原生语义。

### 3.7 视觉质量整体好，但“所有主题都把左侧当安全区”已经限制体系扩展

68/68 主题声明 `safeArea=left`，渲染器也把 wash 固定到左侧。部分左侧视觉复杂度最高的主题恰好是受欢迎的高细节场景，这会与导航、任务文案和 composer 竞争。下一阶段应从单一左安全区升级为多个 UI 占位模板与方向化 grading。

## 4. 发布建议

### 可以继续的工作

- Gallery 继续公开展示与接受主题提案。
- 继续维护哈希、Provenance、代码隔离、真实应用截图与版本绑定。
- 小规模修正文案、主题 Token 和文档可以正常发布。

### Theme Manager 下一次正式稳定发布前建议完成

1. 网络响应硬上限与缓存原子替换。
2. Full Skin 候选 Session 事务化和多 target 回滚。
3. Windows 正常关闭优先、强制终止需明确确认。
4. 目标发现结构化错误，不再折叠为空列表。
5. 授权对话框焦点管理与关键键盘交互。
6. CI 验证 job 最小权限，release 权限隔离。

### 主题规模继续扩张前建议完成

1. 增量生成、有界并发、单次解码与流式写入。
2. 干净检出测试契约与生成产物复用。
3. Gallery/Desktop 缩略图层。
4. Focal-aware crop 与安全区视觉 Gate。
5. 单一元数据源和数量/版本漂移测试。

## 5. 风险优先级

| 优先级 | 数量 | 定义 | 处理建议 |
|---|---:|---|---|
| P0 | 0 | 已确认会导致严重安全事件、数据破坏或不可接受发布风险 | 本次未发现 P0 |
| P1 | 13 | 对发布可靠性、用户数据安全感、构建可持续性或核心交互有直接影响 | 下一轮工程迭代优先完成 |
| P2 | 19 | 明确问题，会随规模、平台或贡献者增长放大 | 在 4–6 周计划中分批处理 |
| P3 | 2 | 产品打磨与治理改善 | 与相关 P1/P2 合并实施 |

## 6. 立即执行的五件事

1. 把 `npm test` 拆成 source-only 与 generated-artifact 两层，并让干净检出默认测试通过。
2. 生成一次并作为 CI artifact 复用，随后再做增量生成器重构。
3. 先完成响应流式硬上限，再处理 Registry 独立签名。
4. 将 Full Skin 应用改成 prepare → inject → verify → commit → cleanup 的事务状态机。
5. 生成多尺寸缩略图，Gallery 卡片和 Desktop 列表不再解码证据 PNG。
